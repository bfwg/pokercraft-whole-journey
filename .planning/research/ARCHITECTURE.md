# Architecture Patterns

**Domain:** Chrome MV3 Extension — Network Interception & Request Splitting
**Researched:** 2026-04-22

## Recommended Architecture

Three-layer architecture: **Content Script** → **Injected Page Script** → **Service Worker (optional coordinator)**.

The critical insight for this project: MV3 content scripts run in an isolated world and **cannot** intercept `fetch`/`XHR` calls made by the page's JS. You must inject a script into the **page's main world** to monkey-patch `window.fetch` and `XMLHttpRequest`. This is the only way to transparently intercept, split, and merge API calls before the Angular app processes responses.

```
┌─────────────────────────────────────────────────┐
│  Pokercraft Angular App (main world)            │
│                                                 │
│   fetch("/api/session/list/Holdem?from=X&to=Y") │
│         │                                       │
│         ▼                                       │
│  ┌─────────────────────────────────┐            │
│  │  Injected Page Script           │            │
│  │  (runs in main world)          │            │
│  │                                 │            │
│  │  1. Intercept fetch()          │            │
│  │  2. Parse date range            │            │
│  │  3. Split into 25-day chunks    │            │
│  │  4. Fire N real fetch() calls   │            │
│  │  5. Decrypt & merge responses   │            │
│  │  6. Re-encrypt merged result    │            │
│  │  7. Return single Response      │            │
│  └─────────────────────────────────┘            │
│         │                                       │
│         ▼                                       │
│   App receives merged response (transparent)    │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  Content Script (isolated world)                │
│                                                 │
│  - Injects page script into main world          │
│  - Patches date picker DOM (if CSS/DOM-based)   │
│  - Relays messages to service worker            │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  Service Worker (background)                    │
│                                                 │
│  - Optional: logging, badge updates, storage    │
│  - NOT needed for core interception             │
└─────────────────────────────────────────────────┘
```

## Component Boundaries

| Component | Responsibility | Communicates With |
|-----------|---------------|-------------------|
| **manifest.json** | Declares permissions, content scripts, host patterns | Chrome runtime |
| **Injected Page Script** (`inject.js`) | Monkey-patches `fetch`, splits requests, merges responses | Pokercraft app (same JS context), Content Script (via `window.postMessage`) |
| **Content Script** (`content.js`) | Injects page script into main world, patches date picker restriction, bridges messaging | Page Script (via `window.postMessage`), Service Worker (via `chrome.runtime`) |
| **Service Worker** (`background.js`) | Badge/icon state, optional logging or storage | Content Script (via `chrome.runtime.onMessage`) |

## Data Flow

### Core Flow: Request Interception & Splitting

```
1. App calls fetch("/api/session/list/Holdem?from=1700000000000&to=1710000000000")

2. Injected script's patched fetch() catches it:
   - URL matches /session/list/Holdem pattern? YES
   - Date range > 25 days? YES → split needed

3. Calculate chunks:
   - Chunk 1: from=1700000000000, to=1702160000000 (25 days)
   - Chunk 2: from=1702160000000, to=1704320000000
   - ...etc

4. For each chunk:
   - Call original fetch() with chunk's date range
   - The app's own DPoP generation runs naturally because we're
     calling real fetch() from the same JS context
   
   CRITICAL: DPoP tokens are generated by interceptors/middleware
   attached to fetch. If the app uses Angular HttpClient (not raw
   fetch), the interception point may need to be at XHR level instead.
   Must verify at runtime which API the app actually uses.

5. Collect all responses, decrypt each (AES-CBC, key from header `a`)

6. Merge:
   - Concatenate sessionIds arrays
   - Set fromTime = min of all chunks
   - Set toTime = max of all chunks  
   - Set remain = remain from last chunk (or 0)

7. Re-encrypt merged payload, construct synthetic Response object

8. Return synthetic Response to the app's .then() chain
```

### DPoP Token Challenge

This is the hardest architectural problem. DPoP tokens must be:
- Generated per-request (unique `jti`, current `iat`)
- Signed with ES256 using the app's ephemeral key pair
- Bound to the specific URL being requested

**Two approaches:**

| Approach | How | Risk |
|----------|-----|------|
| **A: Let app generate naturally** | Call original `fetch()` for each chunk — if DPoP is added via a fetch wrapper/interceptor in the app, it auto-generates | Only works if DPoP is in a fetch interceptor, not pre-computed |
| **B: Extract key & sign ourselves** | Find the app's CryptoKey in memory, generate DPoP JWTs manually | Complex; key may be in closure scope, hard to extract |

**Recommendation:** Start with Approach A. Monkey-patch `fetch` at the lowest level (before any app interceptors). Then when calling `originalFetch()` for each chunk, the app's own DPoP interceptor (if it wraps fetch) will fire. If the app uses Angular's `HttpClient` → `HttpInterceptor` → `XHR`, then patch `XMLHttpRequest.prototype.open/send` instead.

**Runtime investigation needed:** Open DevTools, make a session/list request, set breakpoint on `fetch` and `XMLHttpRequest.send` to see which path the app uses and where DPoP gets attached.

### Date Picker Patching

Two possible approaches depending on how the restriction is implemented:

1. **DOM-level:** If Angular uses `max` attribute on a date input or a config object, the content script can observe and modify DOM attributes via MutationObserver.

2. **JS-level:** If the restriction is in Angular component logic (comparing dates in TS), the injected page script must find and override the validation function. Given obfuscation, runtime patching (finding the component instance via Angular debug tools or prototype patching) is more reliable than static analysis.

**Recommendation:** Use the injected page script to override `Date` comparison or find the Angular component's date validation. The content script handles initial injection only.

## Manifest V3 Specifics

```json
{
  "manifest_version": 3,
  "permissions": [],
  "host_permissions": ["https://my.pokercraft.com/*"],
  "content_scripts": [{
    "matches": ["https://my.pokercraft.com/*"],
    "js": ["content.js"],
    "run_at": "document_start"
  }]
}
```

**Key MV3 constraints:**
- No `webRequestBlocking` — cannot modify requests via background script. This is why page-level interception is mandatory.
- Content scripts with `"world": "MAIN"` (Chrome 111+) can run directly in the page context, eliminating the need for dynamic script injection. Use this instead of `document.createElement('script')`.
- Service worker replaces background page — no persistent state, but not needed here.

### Main World Content Script (Modern MV3)

```json
"content_scripts": [
  {
    "matches": ["https://my.pokercraft.com/*"],
    "js": ["inject.js"],
    "run_at": "document_start",
    "world": "MAIN"
  },
  {
    "matches": ["https://my.pokercraft.com/*"],
    "js": ["content.js"],
    "run_at": "document_start",
    "world": "ISOLATED"
  }
]
```

This is cleaner than dynamic injection and avoids CSP issues with inline scripts.

## Patterns to Follow

### Pattern 1: Fetch Monkey-Patch with Selective Interception

```javascript
// inject.js (MAIN world)
const originalFetch = window.fetch;

window.fetch = async function(input, init) {
  const url = (input instanceof Request) ? input.url : input;
  
  if (!url.includes('/api/session/list/Holdem')) {
    return originalFetch.call(this, input, init);
  }
  
  const parsed = new URL(url);
  const from = Number(parsed.searchParams.get('from'));
  const to = Number(parsed.searchParams.get('to'));
  
  const CHUNK_MS = 25 * 24 * 60 * 60 * 1000;
  if (to - from <= CHUNK_MS) {
    return originalFetch.call(this, input, init);
  }
  
  // Split into chunks and fetch each
  const chunks = splitDateRange(from, to, CHUNK_MS);
  const responses = await Promise.all(
    chunks.map(([f, t]) => {
      const chunkUrl = new URL(url);
      chunkUrl.searchParams.set('from', f);
      chunkUrl.searchParams.set('to', t);
      return originalFetch.call(this, chunkUrl.toString(), init);
    })
  );
  
  // Decrypt, merge, re-encrypt, return synthetic Response
  return mergeResponses(responses);
};
```

### Pattern 2: XHR Interception (if Angular uses HttpClient)

```javascript
const origOpen = XMLHttpRequest.prototype.open;
const origSend = XMLHttpRequest.prototype.send;

XMLHttpRequest.prototype.open = function(method, url, ...args) {
  this._interceptUrl = url;
  return origOpen.call(this, method, url, ...args);
};

XMLHttpRequest.prototype.send = function(body) {
  if (this._interceptUrl?.includes('/api/session/list/Holdem')) {
    // Intercept and handle splitting
    handleSplitXHR(this, this._interceptUrl, body);
    return;
  }
  return origSend.call(this, body);
};
```

## Anti-Patterns to Avoid

### Anti-Pattern 1: Using declarativeNetRequest for this
**What:** Trying to use MV3's `declarativeNetRequest` API to modify requests
**Why bad:** It can redirect/block/modify headers but cannot split one request into many or merge response bodies. Wrong tool entirely.

### Anti-Pattern 2: Proxying through Service Worker
**What:** Routing requests through the background service worker
**Why bad:** MV3 service workers can't use `webRequestBlocking`. Also adds unnecessary complexity and latency. The page script can handle everything.

### Anti-Pattern 3: Pre-computing all DPoP tokens
**What:** Generating all chunk DPoP tokens before making requests
**Why bad:** DPoP includes `iat` (issued-at timestamp). If you pre-generate, clock skew on slow networks could invalidate tokens. Let each request generate its own token naturally.

## Suggested Build Order

Based on dependencies:

1. **Phase 1: Minimal extension scaffold + fetch/XHR discovery**
   - Create manifest.json with MAIN world content script
   - Inject a script that logs all fetch/XHR calls on Pokercraft
   - Determine: does the app use fetch or XHR? Where does DPoP attach?
   - Deliverable: working extension that observes without modifying

2. **Phase 2: Single-request interception (no splitting)**
   - Monkey-patch the correct API (fetch or XHR)
   - Intercept session/list calls, log params, pass through unchanged
   - Verify interception works without breaking the app
   - Deliverable: transparent passthrough proving interception works

3. **Phase 3: Request splitting + response merging**
   - Implement date range chunking logic
   - Implement decrypt → merge → re-encrypt pipeline
   - Use existing `decode.js` logic for AES-CBC decryption
   - Deliverable: large date ranges return merged data

4. **Phase 4: Date picker UI patch**
   - Locate and disable the 3-month restriction in the date picker
   - This is independent of the API work but needs runtime analysis
   - Deliverable: user can select arbitrary date ranges

**Dependency chain:** Phase 1 → Phase 2 → Phase 3. Phase 4 is parallel (can start anytime after Phase 1).

## Scalability Considerations

Not applicable — this is a single-user browser extension. No server-side concerns.

**Performance note:** A 1-year date range = ~15 sequential API calls. Consider:
- Show progress indicator via badge or injected DOM element
- Implement concurrency limit (2-3 parallel requests) to avoid rate limiting
- Cache responses in `chrome.storage.local` to avoid re-fetching
